# 帖子评论二级回复与点赞设计

## 1. 交互边界

帖子详情采用“一级评论 + 一层回复”结构。用户可以回复一级评论，也可以回复某条已有回复；后者仍归入原一级评论下，并显示“回复 @鹏宇用户xxxx”。页面不继续增加第三层缩进，避免手机界面过窄和讨论关系失控。

每条一级评论和回复都提供“回复”“赞”两个操作。评论点赞为可切换状态：同一用户第一次点击点赞，再次点击取消；请求进行期间锁定该条评论，避免连续点击造成重复写入。

## 2. 数据模型

`comments` 新增兼容字段：

- `parentId`：一级评论为空；回复保存所属一级评论 ID。
- `replyToCommentId`：实际被回复的评论或回复 ID。
- `replyToUserId`、`replyToAliasNo`、`replyToDisplayName`：用于展示回复对象。
- `likeCount`：评论当前点赞数，旧数据按 0 处理。

新增私有集合 `comment_likes`：

- `_openid`：点赞用户。
- `commentId`：被点赞评论。
- `targetType`、`targetId`：所属业务对象，便于后续清理。
- `createdAt`：点赞时间。

`(_openid, commentId)` 必须建立唯一组合索引，确保一个用户对一条评论最多只有一条点赞记录。集合应用客户端不可读写规则，所有操作经过 `comments` 云函数。

## 3. 接口

- `comments.add` 新增可选参数 `replyToCommentId`。服务端读取目标评论并核对 `targetType/targetId`，不能跨帖子伪造回复关系。
- `comments.list` 返回平铺评论、回复关系、`likeCount` 和当前用户的 `liked` 状态。前端组装为一层讨论树。
- `comments.toggleLike` 校验登录和评论存在性，新增或删除 `comment_likes` 记录，并原子增减评论点赞数。

回复正文继续执行微信内容安全检测。旧评论不需要迁移：缺少 `parentId` 时按一级评论显示，缺少 `likeCount` 时按 0 显示。

## 4. 异常处理

- 被回复评论不存在或不属于当前帖子：拒绝发送。
- 未登录：引导登录，不进入回复或点赞流程。
- 点赞请求未完成：忽略同一评论的再次点击。
- 主评论缺失但回复仍存在：前端将孤立回复作为普通评论展示，避免内容静默丢失。
- `comment_likes` 尚未创建：旧评论列表仍能加载，但点赞操作需要完成集合与云函数部署后才能使用。

## 5. 验收清单

1. 回复一级评论后显示在该评论下方。
2. 回复某条回复后仍在同一组内，并正确显示回复对象。
3. 点赞从 0 变 1，再点恢复 0；刷新页面状态保持一致。
4. 两个用户可以分别点赞同一评论，数字正确累加。
5. 旧评论正常展示为一级评论和 0 赞。
6. 快速连续点击不会重复增加点赞数。
7. 不能使用其他帖子中的评论 ID 建立跨帖回复。
