# 二手回收转账接入与实施计划

> 后续设计入口：[市场回收逻辑主设计](2026-09-05-market-recovery-logic-design.md)及[API / 接口安全填写表](../wechat-transfer-api-security-fill-sheet.md)。本文保留已完成修正与测试记录；第 4 节原拟新增独立云函数的布局，已由主设计中的单一支付出口、内部模块划分替代。后续实现以主设计为准。

**目标：** 在用户选择的“平台真实回收、再销售”模式下，为回收款领取接入商家转账（场景 1010），分别记录回收、销售和付款。

**架构：** 用户与平台形成回收订单，平台作为销售方向买家出售已收购商品。回收应付款独立于买家销售订单；用户领取已确认回收款时，由服务端创建付款单并调用微信商家转账。微信回调和查单负责确认到账，小程序确认收款页面只负责交互。

**技术栈：** 原生微信小程序、CloudBase 云函数/数据库事务、现有 Node.js HTTP 支付函数、微信支付 API v3。

**当前状态（2026-09-05）：** 用户自行申请开通二手回收。尚未收到正式开通结果。本次先完成接口参数校验修正、配置核对和实施计划，不代表回收业务、钱包或提现已经实现；没有部署和实际资金操作。

## 1. 本次选择与分账的关系

前一份审查针对“个人互卖、平台撮合”。用户现在选择按平台实际回收后销售的路线申请；这是业务调整，不是仅改变转账备注。

| 资金环节 | 本方案采用的能力 | 业务依据 |
| --- | --- | --- |
| 买家向平台购买已收购商品 | 已有小程序/JSAPI 支付能力，另接入回收商品销售订单 | 平台销售订单 |
| 平台向原物主支付回收款 | 商家转账，真实场景 1010 | 已确认的回收订单及交付记录 |
| 平台销售收入、回收成本与费用 | 本地财务记录与渠道对账 | 两类订单分别入账 |
| 将一笔交易款分给第三方合作商户 | 当前回收首版没有这项需求，不把分账作为必开项 | 将来新增合作分成时再单独设计 |

因此，当前方案需要收款和转账能力，不依赖分账产品。普通分账只解决符合产品条件的订单资金分配；开通分账不等于建立个人卖家结算资格，也不能代替应付回收款账务。

平台确认收购之后，不能以商品尚未再次售出为由，在系统中擅自抹去应付回收款。回收交付、验货、报价接受和付款期限应在回收订单中明确；本计划不擅自设定具体期限。原物主对平台的回收款债权与买家对平台的售后退款分别处理。

## 2. 开通后需要确认的设置

不用重新申请已经关联的 AppID，也不要因为新增转账就重置在用的密钥。

1. 在商家转账产品设置中确认正式状态、已获批场景 1010、单笔及日/月累计额度、可用发起方式；若需要开启 API 发起，由商户本人按平台流程设置。申请页预览不是正式权限。
2. 按平台要求配置接口安全 IP。填写实际部署后端的公网出口 IP，不是开发电脑 IP、小程序请求域名或支付回调域名。云函数出口未固定时，先核实部署服务的固定出口方案，不填任意 IP。
3. 核对原支付函数使用的商户、AppID、APIv3 密钥、商户证书私钥及证书序列号；私钥、APIv3 密钥只放服务端受保护配置，不发聊天、不提交仓库。
4. 核对微信支付公钥与 ID 或现有受支持的平台证书验签配置。微信支付公钥与商户 API 证书私钥是不同材料，不能互相代替。
5. 准备独立的转账结果通知地址。是否使用现有网关转发必须以该网关实际支持的转账回调为准，不能套用支付通知地址。
6. 运营账户出资并按平台渠道充值。充值和真实转账由用户操作或单次明确授权；本地校验测试不需要充值。

用户只需提供开通状态、最终额度、发起方式、证书/公钥“是否已配置”等非秘密信息。不要把本地进程缺少环境变量误判成已部署云函数缺少密钥；云端配置仍须在对应环境核对。

### 当前代码读取的配置名

配置位置：`cloudfunctions/pengyu-pay-fj7pei2f-demo-scfweb/config/config.js`。

| 环境变量 | 用途 | 本次处理 |
| --- | --- | --- |
| `appId` | 小程序 AppID，转账收款人 OpenID 所属应用 | 核对现有配置，不能用其他 AppID 的 OpenID |
| `merchantId` | 当前普通商户号 | 核对与开通转账的商户一致 |
| `merchantSerialNumber` | 商户 API 证书序列号 | 核对与在用私钥配套 |
| `privateKey` | 商户 API 私钥，请求签名 | 只在服务端配置 |
| `apiV3Key` | APIv3 密钥，通知解密 | 沿用对应商户的在用值 |
| `wxPayPublicKey` / `wxPayPublicKeyId` | 微信支付公钥和 ID，验签 | 成对配置；现有证书模式需独立验证，不盲目切换 |
| `signMode` | `sdk` 或 `gateway`，通知验证方式 | 沿用经过验证的方式，转账通知单独验证可信来源 |
| `transferNotifyUrl` | 转账通知 URL | HTTPS、公网可达、无查询参数 |

源码没有自动加载 `.env` 的逻辑；仅创建 `.env` 文件不会让部署环境生效。实际密钥需在支付函数所属环境配置。

当前转账通知路由是 `/wx-pay/transferTrigger`。SDK 模式的完整地址形如 `https://<实际服务域名>/<实际挂载路径>/wx-pay/transferTrigger`；此处没有已验证的实际公网地址，不直接复制占位符到商户平台。

## 3. 本次接口修正的范围

文件：

- `cloudfunctions/pengyu-pay-fj7pei2f-demo-scfweb/utils/validator.js`
- `cloudfunctions/pengyu-pay-fj7pei2f-demo-scfweb/tests/validator.test.js`
- `cloudfunctions/pengyu-pay-fj7pei2f-demo-scfweb/tests/controller.test.js`
- 对应模板说明与策略注释。

修正点：

1. 区分低额转账与姓名校验：0.30 元是姓名字段规则的阈值，不能据此拒绝 0.10–0.29 元的无姓名转账。基础参数校验允许从 10 分起；正式业务仍必须额外校验本商户最终获批的单笔、商户日累计、用户日累计和商户月累计额度。官方现行个体户规则还列出单月 10 万元限制且暂不支持调整；不能将截图的三个数值当作所有额度。额度核对和规则版本需记录于服务端，未验证的预览不自动写入线上配置。
2. 当前策略没有实现姓名敏感字段加密，保持拒绝 `user_name` 及金额达到 2,000 元的请求。这是代码能力限制，不是商户获批转账额度，也不是“免密额度”。
3. 报备字段使用官方 `info_type` 与 `info_content`；校验非空字符串及长度。场景 1010 固定一条，信息类型为“回收商品名称”，信息内容为 1–32 字符。内容来自服务端回收订单快照，不能由小程序任意声明。该场景不支持红包样式；`user_recv_perception` 可省略，若传入只使用“二手回收货款”。
4. `services/payService.js` 中发起转账和查询转账仍保持明确关闭。不能直接删除这几个拒绝语句，现有控制器允许客户端传入收款人、金额和场景，尚不适合直接暴露为提现接口。
5. 验证合法参数仍不能触发实际付款，防止“修好参数校验”意外变成“已启用提现”。

基础校验测试命令：

```powershell
node --test cloudfunctions/pengyu-pay-fj7pei2f-demo-scfweb/tests/validator.test.js cloudfunctions/pengyu-pay-fj7pei2f-demo-scfweb/tests/controller.test.js
```

## 4. 接下来的业务实现顺序

以下是待实施设计，文件名是拟新增或修改的位置，不表示已经存在。

### 任务一：回收报价与交付

新增 `cloudfunctions/recovery/index.js`、`tests/recovery-orders.test.js`，管理 `recovery_orders`。用户提交回收申请；管理员报价；用户接受报价；平台验收交付；按已接受的约定确认回收应付款。未经用户同意的验货改价必须重新确认。

金额全部存整数分，保存商品、报价、费用规则、双方和时间快照。首版费用规则未定，不擅自套用旧审查中的 1% 示例；如设置费用，要在确认报价时展示扣费与净收款，后续领取不能突然增加收费。无有效费用规则时相关收费功能保持关闭。

管理员权限从服务端用户记录判断，代售点 `outlet_admin` 不自动获得市场资金权限。对原 `goods` 仅建立申请关联，不能将历史“已售”物品直接变成平台库存或用户余额；“求购”也不能自动当作回收出售。

测试：跨用户读取、重复接受、并发验收、报价版本变更、改价再次确认、删除原物品后的订单快照、未验收不得重复确认应付款。

### 任务二：平台库存与销售订单

拟新增 `cloudfunctions/recovery-sales/index.js`、`tests/recovery-sales.test.js`，建立回收来源、唯一库存和平台定价。只有实际完成收购的物品可作为平台库存销售，回收定价与销售定价分别记录。

支付函数为销售订单新增独立业务钩子和受信任的订单类型识别，不把 `goods` 或聊天上下文直接塞进原代售点订单。付款、关单、退货库存、付款与超时竞争需事务和渠道查单协调。

测试：唯一库存并发抢购、买家身份与金额篡改、回调重放、关闭订单后晚到付款、退款失败不能先返还库存。平台销售退款不能重复扣回原物主已经取得的回收款。

### 任务三：应付款账务与领取申请

拟新增 `cloudfunctions/recovery-finance/index.js`、`tests/recovery-finance.test.js`，建立回收应付款、领取申请和不可重复入账的资金流水。用户页面展示“待确认回收款、可领取、领取中、已领取”，与可充值钱包区分。

按业务单和固定请求标识使用事务：同一笔回收款只确认一次；领取时占用可领取金额；错误未知时保留领取中并查单；明确失败才释放，成功终态不回退。回收应付款记录与渠道付款记录可相互核对，金额可由流水复算。

客户端只提交申请 ID 和幂等标识。收款人取可信登录身份和应付款归属；金额、场景、报备商品名称、回调地址取服务端数据。管理员不能通过前端金额参数绕过账务。

测试：并发提现、相同请求重试、不同用户申请、单笔与两个日累计额度及商户月累计额度的并发预留、跨日/月边界、数据库提交失败、渠道超时、用户取消/超时未收款、重复失败通知、失败后晚到成功的异常处置。渠道累计还可能包含同商户其他入口的付款；本地预算不代表渠道剩余额度，仍需处理渠道额度拒绝并核对原单结果。

### 任务四：微信转账与收款确认

拟新增独立 `services/recoveryTransferService.js` 和对应业务控制器；扩展 `miniprogram/utils/payment.js` 或新增专用 `miniprogram/utils/recovery-payment.js` 调起官方确认收款能力。现有原始模板接口不作为客户端可自由指定收款人金额的入口。

服务端调用 `/v3/fund-app/mch-transfer/transfer-bills`。每次已授权领取固定商户转账单号，超时和未知结果先查原单，不能换号再付。仅对属于当前登录用户、处于待确认的付款单返回官方收款凭证，不记到公开日志。

小程序先用 `wx.canIUse('requestMerchantTransfer')` 检查能力，再调用 `wx.requestMerchantTransfer({ mchId, appId, package: package_info, ... })`。处理 `WAIT_USER_CONFIRM` 和 `package_info`，用户取消后允许回到同一单继续确认；`ACCEPTED`、`PROCESSING`、`TRANSFERING`、前端 success 都不等于实际到账。经验签回调或可信查单确认 `SUCCESS` 后才记已领取；其他状态按当前官方枚举处理。失败或撤销须核实最终结果后再释放账务预留，不能仅凭本地超时释放。

当前手写 HTTP 策略直接解析响应，未来开启转账前还必须验证微信 API 响应签名；不能仅相信 HTTP 200 或客户端返回。通知也必须验签/验证可信网关、核对商户及业务单号、金额和收款人，再提交账务事务。

### 任务五：页面、条款与联调

拟新增回收订单详情、回收款列表、领取详情、管理员回收与付款管理页；修改 `miniprogram/pages/profile/index.*` 增加入口。原市场中“平台不提供支付”的文案需要按实际启用范围更新；在回收场景启用前不改成已支持真实提现。

隔离环境验收订单、权限、重复回调、余额复算和异常恢复后，再使用商户实际支持的金额和明确授权做真机验证。转账测试下限不能沿用 JSAPI 的 1 分钱支付测试；回收出资测试与买家支付/退款使用独立业务单。

上线前必须同时具备正式产品权限、有效配置、真实回收订单依据、交易与账务完整实现及对账结果。单独开通产品、单独通过本地测试都不等于真实提现完成。
