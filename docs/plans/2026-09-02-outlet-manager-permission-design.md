# 代售点两级管理员权限设计

## 需求与约束

总管理员需要新增、编辑和停用任意代售点，并拥有普通代售点管理员的全部商品权限。普通代售点管理员由开发者分配到唯一代售点，只能初始化本点商品、调整本点库存以及上下架本点商品。权限不能依赖前端按钮或请求参数，跨代售点请求必须由云函数拒绝。

## 方案比较

1. 推荐：保留 `admin` 作为总管理员，新增 `outlet_admin`，并在用户文档保存唯一 `managedOutletId`。模型简单，能直接按数据库文档 ID 做资源级鉴权。
2. 建立 `permissions` 字符串数组。扩展性更高，但当前只有两个角色，会增加发放、校验和迁移复杂度。
3. 用楼栋号绑定管理员。操作直观，但楼栋与代售点并非稳定的一对一主键，重命名或新增点时容易越权或失联。

## 数据与调用链

`users.role` 允许 `user`、`outlet_admin`、`admin`。普通代售点管理员还必须具备 `managedOutletId`。登录函数只返回当前用户自己的角色和管理范围；角色仍只能由开发者在云数据库发放。

所有管理调用先由 `store` 云函数根据 OpenID 查询用户，再按角色生成管理上下文。对于商品写操作，云函数先读取商品文档，以文档真实 `outletId` 和 `managedOutletId` 比较，不信任客户端传入的代售点。普通管理员不能新增商品或修改名称、价格、图片等商品资料，只能修改已有商品库存和状态；商品表初始化只补齐本点缺失商品且不重置库存。总管理员沿用完整管理能力。

## 失败方式与验收

未分配代售点的 `outlet_admin` 返回“尚未分配代售点”；跨点访问返回“无权管理该代售点”；普通管理员调用新增代售点、编辑代售点、新增商品或修改商品资料均由云端拒绝。总管理员能完成全部操作。管理页根据云端范围只展示允许的入口，但前端隐藏不作为安全边界。

非功能要求：不新增集合和索引；权限查询沿用 `users._openid` 索引；单次列表不超过 100 条；现有 `user` 与 `admin` 数据保持兼容。
